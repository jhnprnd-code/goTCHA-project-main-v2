# Data provenance

## Short version

- Every number in `results/` was computed from one file, `backend/sessions_model_training.jsonl`: 117 records, of which 87 are scored (27 timed human sessions from 9 people, 60 timed bot sessions from 20 bot runs) and 30 are practice levels that the evaluation skips.
- The original, unmodified study log was not preserved. Nothing in the repository can show that no human session was left out before that file was put together.
- The bot data adds no independent check. It was generated by scripts we wrote, and the committed bot file was extracted from the training file.
- Until now the result files carried no checksum, so they could not be tied to a particular version of the data. `evaluate.py`, `permutation_test.py`, `train.py` and `diff_filter.py` now record a SHA-256 of every data file they read. `freeze_data.py` preserves the files from here on.
- **The committed model card has no fingerprint yet.** `backend/model.joblib.card.json` (trained 2026-10-21 10:45) and `results/report.md` (generated 10:31) were written by the scripts as they were before the checksum change: that clone had not yet pulled it, and its commit's parent predates it. So nothing in the repository ties the current model to a particular data file. Pull `main`, then rerun `train.py` and `evaluate.py` (step 2 below).

## What the committed checks show

All three come from `machine-learning/diff_filter.py`, matching records on `(pid, level_idx, ts)`.

| Output | Left file | Right file | Finding |
|---|---|---|---|
| `diff_filter.txt` | `sessions.jsonl`: 37 records, all human (27 timed, 10 practice), all valid | `sessions_model_training.jsonl`: 117 | The training file is those 37 records plus 80 bot records. Nothing from `sessions.jsonl` is missing from it. |
| `diff_filter_bots.txt` | `sessions_bots.jsonl`: 80 records | `sessions_model_training.jsonl`: 117 | The 80 bot records are all in the training file. The training file also has the 37 human records. |
| `diff_filter_original.txt` | `sessions_backup.jsonl`: 117 records | `sessions_model_training.jsonl`: 117 | Same 117 sessions. |

`diff_filter_reverse.txt` is the first comparison run one way only, with the training file as the left side: the 80 records it lists are the bot records.

## What they do not show

1. **The original log is gone.** The server appends every submitted level to `sessions.jsonl`, including levels flagged invalid (for example by the frame-stutter gate), and every live `/verify` call as an unlabeled record. The current `sessions.jsonl` has 37 lines, all valid human levels, none flagged and no unlabeled traffic. That is what a run with no flagged levels and no live traffic would look like. It is also what a log that was filtered before the comparison would look like. The comparison cannot tell these apart, because the original it would need is the file that was lost.
2. **`sessions_backup.jsonl` is not the original either.** It is an assembled file (human and bot records together) with the same 117 sessions as the training file, so matching it proves only that the training file was not changed afterwards.
3. **The bot comparison is circular.** The 80 bot records in `sessions_bots.jsonl` came out of the training file, so finding them in the training file says nothing about where they came from originally.
4. **The bot sample cannot be regenerated.** The `pw_*` records come from `admin-and-tests/bot_playwright.py`. It is seeded, but the fitted and replay attackers draw on the human sessions, every record gets a new participant code and timestamp, and the seeds and arguments used for these runs were not written down. A rerun produces a different sample, so the 60 scored bot sessions exist only in these files.

The pilot model was trained on 2026-10-17, 2026-10-20 and 2026-10-21, and the three cards have the same threshold and the same out-of-fold AUC (0.7230) to full precision. The 2026-10-21 rerun of `evaluate.py` also reproduced `report.md` and `metrics.json` apart from the timestamp. That is consistent with the same data on all three days. It is not a checksum.

## What can honestly be claimed

> The evaluation used a 117-record file assembled from the study log and the bot runs. The original unmodified log was not preserved, so we cannot independently show that no human session was excluded before assembly. All 37 human records in the file are valid, unflagged levels: 27 timed levels from the 9 participants who completed the study, and 10 practice levels (one per completer plus one from a participant who dropped out). The bot sessions come from attackers we wrote and cannot be regenerated.

That is a limitation of this pilot, and it belongs next to the small sample size, not behind it.

## From now on

A freeze made today preserves what exists today. It does not recover the lost original. What it does is stop the next question ("is this the file the numbers came from?") from being unanswerable.

1. **Stop the server**, then freeze the working files to a folder outside the project (a USB drive or a synced folder):

   ```
   python admin-and-tests\freeze_data.py --dest D:\goTCHA_frozen_20261021 --manifest results\data_manifest.json
   ```

   With no file names it takes whichever of `sessions.jsonl`, `consent.jsonl`, `sessions_model_training.jsonl`, `sessions_bots.jsonl` and `sessions_backup.jsonl` exist in `backend/`. The copies are made read-only and checked byte for byte against the source. A different file already in `--dest` is never overwritten. `results/data_manifest.json` holds file names, SHA-256 values, line counts and sizes, no data, and can be committed.

2. **Pull `main`, then rerun the scripts** so their outputs carry the checksum (commands in `README.md`): `train.py`, `evaluate.py`, `permutation_test.py`. Pull first with `git pull --ff-only`: a copy of the scripts from before the change writes no fingerprint and says nothing about it. Afterwards `report.md` opens with a `Data read:` line, and `metrics.json`, `permutation.json` and the model card carry a `data_files` entry. If any of them lacks it, the scripts that wrote it were out of date.

3. **Check any time** that the working files still match the frozen ones:

   ```
   python admin-and-tests\freeze_data.py --verify results\data_manifest.json --dir backend
   ```

   It exits with an error and names the file if anything differs or is missing.

4. **Quote a number with its file.** A figure from `report.md` is tied to the `sha256` printed on its `Data read:` line, and that value should equal the one in `data_manifest.json`. If they differ, the figure does not describe the frozen data.
